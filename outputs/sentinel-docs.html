Part I

Product Overview

What Bolt Sentinel is, the manual-compliance problem it removes, the four surfaces it ships, and the governance principles that bind everything it does.

1.1 What Bolt Sentinel is

Bolt Sentinel is an AI-native Regulatory Operations Platform for a ride-hailing super-app operating across six markets, Estonia (Tallinn), Poland (Warsaw), Portugal (Lisbon/Porto), Romania (Bucharest), Nigeria (Lagos), and South Africa (Johannesburg/Cape Town). It is a single, integrated, production-grade platform that automates the highest-effort manual compliance work in ride-hailing central operations.

It presents to users as one platform with four operational surfaces sitting on a shared compliance-intelligence core. Each surface follows the same computational shape, ingest unstructured input → interpret it against a market-specific regulatory ruleset → validate or retrieve the relevant data → produce a governed, fully-traceable output, with explainability on every field, an immutable audit trail, and a human decision required before anything binds.

SurfaceWhat it doesWho uses it
A: Authority Request Response (ARR)Interpret a regulator's request, map it to that market's legal requirements, retrieve the data, and produce a compliant, traceable report for human review and submission.Local operations / compliance staff
B1: Fleet Partner OnboardingValidate a partner's document pack against market rules, cross-check across documents, risk-score, and draft a go/no-go decision for a human.Fleet operations / compliance staff
B2: Ongoing Compliance MonitoringContinuously watch the live partner portfolio for expiries and drift, re-validate on renewal, and proactively re-trigger human review.Fleet operations / compliance monitors
C: Regulation IntakeUpload a regulation; AI reads it, classifies the jurisdiction, and proposes a complete executable market ruleset that a human reviews and activates, this is how rules stay current.Regulatory authors / compliance leads

The platform operates across all six markets from a single console, styled in Bolt's design language.

1.2 The problem it solves

A ride-hailing platform operating across many countries faces an enormous, non-uniform regulatory surface. Every market has its own transport-licensing regime, document requirements for fleet partners and drivers, data-residency/privacy/retention/lawful-basis constraints (GDPR variants across the EU; NDPA in Nigeria; POPIA in South Africa), and authority reporting obligations. Two workflows consume the most manual effort.

Problem A: Authority Request Response

Local operations teams receive regular, ad-hoc requests from regulators ("provide all drivers who operated in central Lisbon during Q1 2026, with license validity and total trips"). Today an ops person must interpret what is actually being asked, know the market-specific legal requirements and acceptable format, figure out which internal systems hold the data, pull and cross-reference it, assemble a compliant report, and get it reviewed. This takes hours to days per request, recurs across many markets, and carries legal and financial risk if done wrong or late. The knowledge of "how to answer this authority in this market" lives in local staff heads and does not scale.

Problem B: Fleet Partner Compliance

A fleet partner is a company running multiple vehicles and drivers on the platform. Onboarding (B1) means collecting and validating a market-specific document set, operator licenses, commercial insurance, vehicle registrations and inspection certificates, driver certifications, tax/business registration, for authenticity, completeness and internal consistency, then making a go/no-go call. Monitoring (B2) is the fact that compliance is not static: documents expire on rolling schedules, fleets change, regulations update. Lapses today go unnoticed until they become incidents.

Why one platform

All four surfaces are computationally the same shape, and the market-rule layer, document/text understanding, governance/audit/human-in-the-loop layer, and explainability + accuracy layer are common infrastructure. Building them once and serving multiple compliance workflows is simply how a serious platform is built. To the user it is one integrated regulatory-operations platform.

1.3 The four operational surfaces at a glance

Surfaces A, B1, and C are re-entrant pipelines driven by one runner; B2 is a continuous monitoring loop over the live portfolio that reuses B1's validation machinery. Each pipeline runs live Claude calls one stage at a time, persisting output, confidence and timing so the UI streams progress.

1.4 The value contrast: hours to seconds

The persuasion device is threaded throughout the product: "this took a person half a day; watch it happen in seconds." Manual baselines are configurable per workflow (ARR default 240 minutes, onboarding 360, regulation intake 480) and clearly labelled estimates. Sentinel surfaces the contrast in several places:

  • Per-item completion, a "Manual baseline ~Xh / Sentinel Ys" banner on each completed request or onboarding, using the real elapsed AI processing time (aiElapsedMs).
  • Per-stage timing, the pipeline stepper shows how long each AI stage took.
  • Portfolio level, the Home dashboard shows cumulative hours saved this period plus the total AI cost (the capital-efficiency story: hours saved against dollars spent).
  • Audit/report footer, elapsed time, model used, and cost per artifact for traceability.

1.5 Governance non-negotiables

The Operational Surfaces

A feature-by-feature deep dive into each of the four surfaces and every shared screen, what they do, the pipeline behind them, every panel and interaction, and the sub-features.

2.1 Surface A: Authority Request Response (ARR)

A regulator sends a request; Sentinel interprets it, maps it to the market's legal requirements, retrieves the data deterministically, generates a compliant report with per-figure provenance, self-validates it, and hands a review-ready artifact to a human. The system never submits to the authority, a human approves, and an export is produced for them to submit.

The end-to-end flow

A request is created with a reference like ARR-EE-0007, a title, the authority, optional cited legal basis, the raw text (or a source PDF), a market, a deadline, and a manual baseline. It starts in status RECEIVED and runs through a six-stage pipeline (surface ARR):

#StageAgent / tierWhat happens
1Intake → IntentIntakeAgent · balanced · intake.request.v1Parses the free text/PDF into a structured RequestIntent: summary, authority, legal basis, purpose, subject types (driver/vehicle/fleet partner/trip), requested fields, filters (zone, period, status), deadline, ambiguities, and a confidence. Gate: if any ambiguity is found (only ever raised when the reporting period is undeterminable, e.g. "the period referenced in our earlier letter") the request transitions to NEEDS_CLARIFICATION and the pipeline blocks for a human.
2Rule mapping → Compliance planRuleMappingAgent · reasoning · rules.interpret.v1Reasons over the market ruleset (passed as cacheable context) to classify each requested field as ANSWERABLE, CAUTIONED (needs minimization/aggregation), or OUT_OF_SCOPE (overreach / restricted without basis). Produces the mandated report format id, a compliance checklist, and structure notes.
3Retrieval planningRetrievalPlannerAgent · balanced · retrieval.plan.v1Turns the plan into a typed query plan, one query per answerable/cautioned field, using only the ruleset's field keys. It does not touch the database.
4Retrieval + complianceDeterministic (no LLM) + ComplianceConstraintAgentThe deterministic executor runs Prisma queries for every non-out-of-scope field, tagging each figure with its source row ids (real provenance). Then the §7.A constraint framework enforces residency/PII/lawful-basis rules, masking, aggregating, or withholding fields, recording an explainable decision per field.
5Report generationGenerationAgent · reasoning · generation.report.v1Generates the compliant report in the mandated language and structure, using only the computed dataset and copying values exactly. Persists a normalized ReportField row per figure (with provenance + the originating AI call id) for the click-through provenance UI.
6Self-validation + confidenceDeterministic verify + ValidationAgent · reasoning · validation.selfcheck.v1First, a deterministic figure-vs-source check recomputes every figure against its cited rows. Then an adversarial validation pass confirms each checklist item is satisfied and each figure is plausible, flagging blocking discrepancies. Confidence per field is attached; the run completes to PENDING_REVIEW.

On human approval the status becomes APPROVED (approved for submission) and an export is produced. Other human actions: reject, request changes (moves to NEEDS_CLARIFICATION with a note), regenerate (re-runs the pipeline), and clarify (appends a clarification note to the raw text and re-runs).

The request inbox

Lists non-deleted requests scoped to the active market filter, ordered by received date with open statuses floated to the top; the header shows an open count. Columns: reference (mono link), request (title + authority), market, status badge, and a live SLA countdown chip that turns amber within 24 hours of the deadline and red when overdue.

The request workspace

The detail screen is the core ARR experience. A header shows the reference, title, country · authority · legal basis, the SLA chip, and the status. Conditional banners appear for NEEDS_CLARIFICATION (clarification panel), terminal decisions (a decision-outcome banner with reviewer name and timestamp), and a time-saved banner once the run has elapsed.

  • Left rail, the live pipeline stepper (starts the pipeline, polls status every 700ms and drives one stage advance at a time, expandable per-stage output and confidence); the original authority request text; the AI interpretation panel (summary, purpose, subjects, zone, period, ambiguity warnings); and the compliance checklist panel where each item carries a satisfied/✗ icon cross-referenced to the self-validation result, plus a "field disposition" view mapping ANSWERABLE→PASS, OUT_OF_SCOPE→FAIL, CAUTIONED→WARN.
  • Right (main), the generated report rendered as a styled article. Each {{fieldKey}} token in a section body is rendered as a clickable provenance figure. Review actions sit at the top. Below: a "compliance constraints applied" panel (each §7.A decision as allow→PASS / block→FAIL / mask·aggregate→WARN with rule + rationale), a "supporting detail" panel for list-typed fields, and a "self-validation" panel (figures-verified count, an overall confidence meter, and a blocking warning if present).

Provenance figures (click-through to source)

Every figure is an inline button (dashed underline; brand-green with a ✓ if verified, amber with a ⚠ if not). Opening it fetches /api/report-fields/[id]/provenance, which resolves the figure's provenance refs into the real source rows (Driver/Vehicle/Trip/FleetPartner, capped at 50 ids each) and returns the originating AI call's model, prompt version, cost and confidence. The dialog shows the classification, total source-row count, the AI call metadata, and a mini-table per source entity. This realizes the "every figure traces to its source rows + the prompt that produced it" guarantee.

Report export

GET /api/authority-requests/[id]/export?format=pdf|json produces the submission artifact. The PDF (built with pdfkit, lib/report-pdf.ts) carries a Bolt-green header bar with the bolt mark and wordmark, regulator/market/reference, the title, preamble, sections (with {{key}} figure substitution), a "Reported figures" table, the closing, and a footer noting the generation time, model, and report reference for traceability.

Representative request types

The platform handles distinct request types across the six markets: a clean Tallinn Q1 driver/trip request (happy path), an ambiguous Warsaw request referencing an unspecified earlier letter (surfaces a clarification), a Lagos NDPA driver-PII roster (the constraint engine aggregates/masks), a Johannesburg overreach request for per-driver criminal records (flagged out-of-scope), and clean Lisbon and Bucharest requests showing market-specific report formats.

2.2 Surface B1: Fleet Partner Onboarding

A partner submits a document pack; Sentinel reads every document natively, validates each against the market's rules, cross-checks across documents, risk-scores the partner, and drafts an approve / approve-with-conditions / reject decision for a human. The system never auto-decides.

The four-stage pipeline (surface B1)

#StageEngineWhat happens
1Document extractionExtractionAgent · reasoning · extraction.fields.v1For each document, the PDF/image bytes are fed to Claude natively (no separate OCR). Expected fields come from the ruleset's document spec. Per-field calibrated confidence is captured; illegible/absent fields are marked present=false. A document whose overall confidence < 0.70 (or any present field < 0.60) is FLAGGED rather than passed silently; otherwise EXTRACTED. Documents are processed in parallel.
2Validation & cross-checksDeterministic DSL (no LLM)Each document's validation rules are evaluated with the rule DSL (13 operators, regex, date-not-expired, cross-field equals, numeric comparisons, etc.) producing PASS/WARN/FAIL with severity, message, and evidence. Cross-document checks compare fields across documents (e.g. operator-license holder vs business-registration name) producing MATCH/MISMATCH/INDETERMINATE. Completeness is computed as required non-optional docs present for the partner type, yielding a missing-docs list and a completeness %.
3Risk scoringRiskAgent · balanced · risk.score.v1Aggregates signals (doc/vehicle/driver counts, FAIL/WARN counts, cross-check mismatches, low-confidence docs, items expiring within 30 days, expired items) and the market's risk model (weighted factors: completeness 0.30, expiry proximity 0.25, inconsistencies 0.30, fleet size 0.15). Emits a 0-100 score (higher = riskier), a band (LOW/MEDIUM/HIGH), and per-factor contributions with evidence. Supersedes the prior assessment.
4Decision draftGenerationAgent · reasoning · generation.onboarding.v1Drafts a go/no-go: APPROVE / APPROVE_WITH_CONDITIONS / REJECT with conditions and rationale. A low-confidence extraction becomes a required human-verification condition. The pipeline completes to PENDING_REVIEW; a human binds the decision.

The onboarding queue

Lists partners scoped to the market with counts of documents/vehicles/drivers; queue statuses sort to the top; the header reads "x awaiting · y total." Columns: partner (legal name + reference), market, type, fleet summary (vehicles · drivers · docs), completeness bar + %, risk band badge, and status.

The onboarding workspace

  • Documents panel, a document viewer with a left list (FLAGGED ⚠ / VALIDATED ✓ icons), an iframe PDF preview of the original, and an "extracted fields" panel showing each field's value with a confidence meter; missing or low-confidence (< 0.70) fields are highlighted, notes are shown, and a "gaps" footer lists what the model could not extract.
  • Pipeline stepper, runs the onboarding pipeline and streams stage progress.
  • Decision draft panel, the AI's recommended outcome (hint badge while still a draft), rationale, conditions list and confidence meter, with reject / approve / approve-with-conditions actions.
  • Risk assessment panel, score, band badge, explanation, and per-factor contribution bars.
  • Required-documents checklist, "x/y" with present ✓ / missing ✗ per required doc for the partner type.
  • Validation & cross-checks panel, cross-check messages (including "valueA ≠ valueB" on mismatch), non-passing validations, or "All N rules passed."
Representative onboarding cases

A clean Portugal partner (fast approve), a name-mismatch partner whose operator license and business registration disagree (caught by a cross-check), a missing-document Poland partner (checklist gap → approve-with-conditions draft), and a low-confidence-extraction partner whose illegible TVDE license forces mandatory human review via confidence gating.

2.3 Surface B2: Ongoing Compliance Monitoring

Once a partner is onboarded, compliance is continuously monitored over the live portfolio. B2 is a distinct lifecycle with its own state machine and screens, it is not a re-entrant pipeline but a direct-call engine (surfaces/fleet-monitoring/monitor.ts) that reuses B1's validation machinery. It never auto-suspends; it routes drift to a human.

The monitoring sweep

runMonitoringForPartner(partnerId) runs the lifecycle for one partner; runSweep(marketId?) sweeps every APPROVED / CONDITIONS_APPLIED partner. The sweep is triggerable manually (the dashboard "Sweep" button → POST /api/monitoring/sweep) and on a Vercel cron (/api/cron/monitoring-sweep). For each partner:

  1. Deterministic signals, builds an upcoming-expiry list (vehicle inspection/insurance/registration and driver licence within a 30-day horizon, sorted by days-until); detects vehicles added in the last 45 days with no valid registration; detects expired inspections; and computes whether the partner's last-assessed ruleset version is behind the market's active version.
  2. Ruleset re-flag (highest priority), if the partner is on an older ruleset version, status → PENDING_REVIEW and a RULESET_REFLAG compliance event is recorded.
  3. Drift detection, if signals exist, the DriftDetectionAgent (balanced, risk.drift.v1) compares previous vs current state for new vehicles without docs, lapsed documents, and fleet-composition changes; on detected drift the status becomes DRIFT_DETECTED and a DRIFT_DETECTED event is recorded.
  4. Expiry forecast, if upcoming expiries exist, the ExpiryForecastAgent (fast, risk.forecast.v1) contextualizes them into proactive gap predictions with severity (≤7 days CRITICAL, ≤21 HIGH, ≤30 MEDIUM); a still-compliant partner becomes EXPIRING_SOON with an EXPIRY_FORECAST event.
  5. Status application, a human-owned PENDING_REVIEW is preserved; an AI MONITORING_SWEEP audit row is written.

Re-validation on renewal

revalidatePartner(partnerId) (POST /api/partners/[id]/monitoring/revalidate) re-extracts any newly-uploaded (renewed) documents using the same ExtractionAgent, sets them VALIDATED, extends expiring vehicle insurance where an insurance doc was renewed, re-runs the monitoring lifecycle, and, if the partner was EXPIRING_SOON, returns it to COMPLIANT. It records a resolved REVALIDATION event and partner-history entry. No full re-onboarding is needed.

The monitoring dashboard

Scope is APPROVED / CONDITIONS_APPLIED partners, market-filtered. Four KPIs: portfolio compliant %, at-risk partner count, items expiring within 12 weeks, and open alerts. Panels: a portfolio health stacked bar by monitoring status; an expiry pipeline bar chart bucketing vehicle inspection/insurance expiries into six two-week windows over 12 weeks; an at-risk partners table (risk, status, reason); and a proactive alerts list of open compliance events with severity.

The partner monitoring detail

Shows a document & vehicle validity table (plate plus inspection/insurance/registration dates coloured by validity, missing/expired FAIL, within 30 days WARN, else PASS), a merged compliance-history-and-events timeline, and the current risk breakdown. Human actions (POST /api/partners/[id]/monitoring/decision): re-validate, mark remediated, apply conditions, recommend suspension, or clear back to compliant, each creating a partner-history entry and a resolved HUMAN_ACTION event.

Representative monitoring cases

An Estonia partner with two vehicle inspections lapsing in 21 days (expiry forecast + proactive alert + risk bump); an Estonia partner who added two vehicles without valid registration (drift detection flags it); a Poland partner whose insurance expires in 10 days with a hand-built "renewed" insurance PDF ready for re-validation; and the Estonia ruleset bump from v1 to v2 (adding a driver background-check document) which re-flags previously-compliant partners for review.

2.4 Surface C: Regulation Intake

This is how rules stay current. Upload a regulation (PDF or pasted text); AI reads it into quotable sections, classifies the jurisdiction, and synthesizes a complete, executable market ruleset constrained to what the engine can actually run. The draft is quarantined until a human activates it, at which point it becomes a live market or a new version, and affected partners are re-flagged.

The six-stage pipeline (surface REGINTAKE)

#StageAgent / tierWhat happens
1Read regulationRegulationReaderAgent · reasoning · regulation.read.v1Reads the uploaded regulation natively and decomposes it into stable, quotable sections (the provenance source), detecting language (BCP-47), country, regulator and topics.
2Classify jurisdictionRegulationClassifierAgent · balanced · regulation.classify.v1Determines jurisdiction, region (EU/NG/ZA/US/OTHER), privacy regime (GDPR/NDPA/POPIA), currency/locale/timezone, and a suggested market code; decides whether it matches an existing market (a version update) or is a new market.
3Synthesize rulesetRulesetSynthesisAgent · reasoning · ruleset.synthesize.v1"The most consequential agent." Emits a full MarketRuleset using only the executor's closed vocabularies (entities, aggregations, operators). Anything it cannot express is surfaced as unmappedFields / unsupportedClauses, never invented. Each element carries provenance with a verbatim source quote and section id. For updates it keeps stable ids and emits change notes.
4Validate + dry-runDeterministic + ValidationAgent · reasoning · ruleset.validate.v1Runs MarketRulesetSchema.safeParse (schema gate) plus validateRulesetSources (an "executor dry-run" confirming every answerable field's source is actually executable), then an adversarial review of faithfulness/completeness/coherence/privacy-posture. Blocking if the schema fails, sources are not executable, or the review flags critical/high issues.

The intake screens

The list shows up to 100 imports with reference, source (filename or "pasted text"), proposed market (code + version + "new" chip), status chip, confidence, and date; an upload form (drag/drop PDF/PNG/JPEG or paste text) sits above. The detail screen shows the classification chips (country, region, privacy regime, target code+version, new-market vs version-update) and, once a draft exists: proposed required documents, authority-answerable fields, the proposed compliance policy, a "flagged for human wiring" panel (the honest unmapped fields and unsupported clauses), and a provenance panel (up to 40 entries with source quotes and section ids). The right rail holds the decision actions, a validation panel (schema valid / sources executable / blocking chips and issues), a diff panel for updates, and the classification rationale.

Activation: the only path into the rules table

POST /api/regulation-intake/[id]/activate is the sole way a synthesized ruleset becomes live. It re-parses the draft against MarketRulesetSchema (a hard gate), then either creates a new Market + RegulatoryRuleset (new market) or supersedes the prior active version and bumps activeRulesetVersion (update). On an update it re-flags every partner whose last-assessed version is behind the new one (creating RULESET_REFLAG events and moving them COMPLIANT → PENDING_REVIEW), invalidates the ruleset cache, and records a RULESET_ACTIVATED audit row. Reviewers can also save edits to the quarantined draft (PATCH .../draft, re-parsed against the schema) or reject it.

Part III

The AI Engine

The AI-first principle, the single centralized Claude client, the fifteen named agents, multi-tier model routing, the versioned prompt registry, and the cost ledger.

3.1 AI-first principle & the centralized client

Every value-adding stage is a named agent, a typed LLM operation routed to a model tier and backed by a versioned prompt file. A single core invariant governs the whole system: the LLM never queries the database. Planning agents emit a typed query plan; a deterministic executor is the only Prisma caller and tags every row with its primary key. The model plans and narrates; figures are computed in code, so provenance is real.

Exactly one file imports the Anthropic SDK: engine/llm/client.ts. Every call goes through it so that cost, prompt version, latency and confidence are always recorded. Its callLlm<T>() function:

  • Resolves the prompt by id/version from the registry, the model from the routed tier (overridable via Settings), and a default 4096 max tokens.
  • Builds the system text (optionally appending a cacheable market-ruleset context block, marked ephemeral for prompt caching when enabled), and renders {{var}} templates.
  • Attaches documents as native document (PDF) or image blocks, no separate OCR.
  • Forces Structured Outputs by registering a tool whose input schema is the Zod schema converted to JSON Schema, with tool_choice pinned to it; the tool input is then schema.parse()d.
  • Retries up to four attempts with exponential backoff (800·2^n ms + jitter) on retryable statuses (408, 409, 429, 500, 502, 503, 529).
  • Computes cost from a per-model rate card (input/output/cache-write/cache-read per million tokens) in integer micro-USD, extracts confidence from data.confidence/overallConfidence, and writes an AiCallLog row on both success and terminal failure.

A streaming variant, callLlmStream(), powers the assistant, an async generator yielding text deltas with a best-effort ledger row on completion.

4.2 The re-entrant pipeline pattern & runner

A surface defines Pipeline = { surface, stages[] }, where each Stage is { name, label, run(ctx, io) }. Contexts are re-entrant: they carry only entity ids and metadata, and each stage re-reads prior results from the DB and persists its own, so the chain is independently resumable, one stage per invocation.

The runner (engine/pipeline/runner.ts):

  • startPipeline creates a PipelineRun (QUEUED) wired to the entity by surface, creates ordered PipelineStage rows (PENDING), moves the entity to PROCESSING (B2 excepted), and audits PIPELINE_START.
  • advanceOneStage runs exactly one pending stage. It atomically claims the stage with an updateMany(PENDING→RUNNING), if the claim count is zero (a concurrent advance already claimed it) it returns without re-running, preventing double execution and double AI spend. On a blocked result the stage becomes BLOCKED, the run becomes AWAITING_REVIEW, the entity is routed to PENDING_REVIEW, and a PIPELINE_GATE_OPENED audit (actor AI) is written. On success the stage is DONE; on throw it is FAILED and the run FAILED.
  • finishRun completes the run (recording elapsedMs and the entity's aiElapsedMs for the time-saved contrast) and transitions the entity to PENDING_REVIEW.
Why one stage per invocation

Vercel functions have a bounded duration, so no single invocation runs a whole multi-stage AI pipeline. Completed stages are immutable and persisted, so a timeout merely pauses the chain; a resume sweeper (/api/cron/resume-pipelines) finds stalled runs, resets stuck RUNNING stages to PENDING, and continues from the first non-done stage. This also gives the live per-stage progress the UI streams.

4.3 Governance state machines

Four typed transition maps (engine/governance/state.ts) make an illegal status string impossible to write, assertTransition throws on any illegal move, and every transition writes an audit row. No binding, submitted, or suspended state is ever reached without a human action.

4.4 Provenance system

The deterministic executor returns every record tagged with its primary key and the query that fetched it. The GenerationAgent cites only those row ids (Structured Outputs + a deterministic post-check). Each figure is persisted as a normalized ReportField carrying { fieldKey, label, value, classification, confidence, verified, provenance[], aiCallId }. The §7.B layer recomputes the figure from the cited rows to set verified. The UI renders each figure as a click-through to its source rows plus the exact AI call (model, prompt version, cost, confidence) that produced it.

4.5 Hash-chained audit log

Every meaningful action, AI call, constraint decision, gate open/close, human decision, state change, is appended to AuditLog with actor, action, entity, before/after and timestamp, and for AI rows the model, prompt version, cost and confidence. Rows are hash-chained: hash = sha256(prevHash + canonical(payload)) using a deterministic sorted-key JSON, so any tampering breaks the chain downstream. verifyAuditChain() recomputes every hash in order and reports the first break; the Audit view shows a "Verified" / "Broken @ N" integrity badge.

4.6 Document storage driver

A storage-driver interface (put / getBytes / getUrl / delete) abstracts over a local-filesystem implementation (dev) and a Vercel Blob implementation (prod), selected by environment. Document.storageRef holds the key (local) or the full public URL (blob). PDFs are generated ahead of time during data provisioning (Vercel's filesystem is ephemeral/read-only), and bytes are fetched as base64 to feed Claude's native PDF/image input. A guarded route (/api/documents/[...path]) streams stored bytes with the correct content type.

Part V

The Two Critical Subsystems

Governance and correctness are architectural, not bolted on: the §7.A Compliance-Constraint Framework and the §7.B Accuracy & Confidence Layer.

5.1 §7.A: Compliance-Constraint Framework

"How is governance enforced?" has a structural answer. Each market ruleset carries a typed compliancePolicy; middleware enforces it, and every constraint decision is explainable and audited.

The framework (engine/compliance/checks.ts) enforces bright-line rules deterministically; the ComplianceConstraintAgent reasons about and explains decisions but cannot override a hard block. The authoritative deterministicAction resolves, per field:

Field classificationActionRule
OUT_OF_SCOPEblock (withheld)Restricted / special-category disclosure, overreach. Field omitted from the dataset.
CAUTIONED + list value + (restricted or residency-restricted)aggregatePII minimization / cross-border residency, the list value is replaced by its count, relabelled "(aggregated count)."
CAUTIONED (otherwise)allowDisclosure permitted with caution.
ANSWERABLEallowLegal obligation.

Residency-restricted means the policy's crossBorderTransferAllowed is false; restricted means the field is in the policy's restrictedDisclosureFieldKeys. The framework also supports masking (stripping name/licenseNo per row). The LLM enrichment adds a human-readable rationale per field but the deterministic action stands; failures of the LLM call are swallowed so the deterministic decision always holds. The policy covers data residency (storage region, cross-border allowance, allowed transfer regions), PII classification per field, lawful bases (tag → applicable field keys), purpose limitation (declared purposes + restricted-disclosure keys), and retention (document/audit months + auto-purge). This drives the Lagos NDPA residency scenario and the Johannesburg POPIA overreach scenario.

5.2 §7.B: Accuracy & Confidence Layer

"How do you know the AI is right?" has a visible answer, because documents are validated against known ground-truth records, so accuracy is measurable.

Per-field confidence & gating

Every extracted field and generated figure carries a confidence score. Gating thresholds live once in lib/confidence.ts: pass ≥ 0.85 (higher for sensitive 0.92 / financial 0.90 fields), review 0.60-0.85, and block below 0.60. Critically, gateDecision always blocks an unverified figure or a validation mismatch regardless of confidence. The gate is wired into the human-in-the-loop checkpoints.

Figure-vs-source verification

engine/accuracy/verify.ts recomputes each report figure from its cited rows, independent of the LLM, the hard backstop against hallucinated numbers. A figure must (a) match a dataset field, (b) cite a non-empty set of source row ids that is a subset of the dataset's provenance ids, and (c) have a matching value. Any failure marks the figure unverified and should block completion.

Ground-truth eval harness

engine/accuracy/eval.ts measures extraction precision/recall/F1 against the documents' ground-truth answer keys, builds a calibration reliability view (predicted confidence vs actual accuracy per bucket), tracks per-field confidence distribution, computes per-market F1, and measures the defect catch-rate, whether injected low-legibility defects are caught by low confidence. Confidence buckets are 0-50% / 50-70% / 70-85% / 85-100%. All of this is surfaced in the Accuracy view, making correctness visible, a credibility multiplier for a governance-grade product.

Part VI

The Market Ruleset System

The "market = ruleset" abstraction, the MarketRuleset contract, the validation DSL and executor capability surface, and a detailed tour of all six markets.

6.1 Market = ruleset abstraction

The engine never references a market by name. Every rule lives in the DB as a Zod-validated MarketRuleset in the RegulatoryRuleset.content column. The runtime resolver engine/rules/store.ts reads rules from the DB (cached by immutable code:version, with the mutable active-version pointer always read fresh). The built-in six markets are loaded into the DB from versioned TypeScript files under engine/rules/markets/<CODE>/vN.ts; that code is the initial source only. Adding or changing a market is a new ruleset version, produced either through provisioning or through the Regulation Intake surface, never by changing engine code.

6.2 The MarketRuleset contract

A ruleset (engine/types/ruleset.ts) is a single Zod-validated object with these blocks:

6.3 Validation DSL & executor capability surface

Validations use a declarative DSL of 13 operators, EXISTS, NOT_EMPTY, EQUALS, NOT_EQUALS, MATCHES_REGEX, DATE_NOT_EXPIRED, DATE_WITHIN_DAYS, GTE, LTE, GT, LT, IN_SET, CROSS_FIELD_EQUALS, evaluated deterministically (engine/validation/rules.ts) with flexible date parsing (ISO and DD.MM.YYYY / DD/MM/YYYY) and case-insensitive comparison. So even complex per-market validations need no engine code.

Authority-field sources must be executable by the deterministic executor (engine/retrieval/executor.ts); a static validator (validate-sources.ts) keeps the ruleset in lockstep with it. The executor's capability surface:

Part X

RBAC, Authentication & Security

Seven roles, sixteen permissions, session-based auth, and the tamper-evident audit chain.

10.1 Authentication & sessions

Auth is session-based (lib/auth.ts): an opaque 32-byte token in an httpOnly cookie (sentinel_session), sha256-hashed at rest with a server secret; the active role is held in sentinel_role; sessions last 30 days; passwords are bcrypt-hashed. The session user carries a legacy derived role, the assigned RBAC roles, the active role, and the permissions derived from that active role.

10.2 Roles & permissions

Seven roles (lib/rbac.ts): admin, compliance_reviewer, onboarding_officer, compliance_monitor, regulatory_author, authority_liaison, auditor. Sixteen permissions span home, ARR (view/review/export), onboarding (view/decide), monitoring (view/act), rules (view/author), accuracy, audit, assistant, settings (view/manage), and users.manage. Admin holds all; each other role holds a focused subset (e.g. authority_liaison gets ARR view/export, auditor gets read-only across surfaces). Nav links are gated by a permission map, and the Settings RBAC matrix renders the roles × permission-group grid.

Enforcement note

Fine-grained RBAC is enforced at the navigation/UI layer and on the settings routes (ADMIN / users.manage). Most action routes enforce authentication via guard(); surface-level permission gating lives in the nav layer. The binding-state invariant (no AI-driven approval/suspension/activation) is enforced independently in the handlers and state machines.

10.3 Audit & secrets

Every action is appended to the hash-chained audit log (Part IV); the chain is verifiable on demand. Secrets (the Anthropic API key, ingest token hashes) live in a separate secret bag in AppMeta and are never sent to clients, the key endpoint returns only source + last-4, and ingest tokens are revealed once at creation and stored only as sha256 hashes.

Part XI

Markets, Portfolio & Document Processing

How the six markets, partner portfolio, documents, and ground-truth corpus are provisioned, and the operational scripts around them.

11.1 Market & portfolio provisioning

Data provisioning (prisma/seed.ts + prisma/seed-lib/) establishes the six markets from their rulesets (Estonia starting on v1, with v2 staged inactive), the initial user accounts with assigned RBAC roles, and a portfolio of approved, compliant partners per market. Each partner carries localized names, 2 to 4 drivers, 2 to 5 vehicles with market-correct plate formats and validity windows, trip history over the last 180 days biased to central zones, and the market's required documents rendered as PDFs.

Document rendering & the ground-truth corpus

Every document is rendered from a known ground-truth field map (seed-lib/data.ts) into a full A4 certificate (seed-lib/pdf.ts): seven document kinds with per-kind styling, emblems, validity badges, particulars grids, conditions, and a formal footer. Defect markers can be applied (EXPIRED, NAME_MISMATCH, and LOW_LEGIBILITY, which faintly garbles about 35% of characters to genuinely lower extraction confidence) and stored alongside as DocumentGroundTruth, the basis for the §7.B eval harness.

11.2 Representative situations across the surfaces

The platform is provisioned with representative situations across each surface: six authority requests, four onboarding partners, four monitoring situations, and the Estonia ruleset update, described per surface in Part II. A platform reference date (default 2026-06-04) anchors expiry and ambiguity evaluation deterministically.

Part XII

Tech Stack, Deployment & Operations

The production stack, the Next.js 16 conventions the codebase follows, and how it deploys and runs.

12.1 Stack

Next.js 16 (App Router) · TypeScript (strict) · Tailwind v4 · shadcn/ui · Recharts · TanStack Query · Prisma 6 · SQLite (dev) / Turso libSQL (prod) via the Prisma driver adapter · Anthropic Claude (Haiku/Sonnet/Opus tiers, native PDF/image, Structured Outputs) · Vercel Blob storage · pdfkit · bcryptjs · Zod 4 · React 19. Deployable on Vercel.

12.2 Next.js 16 conventions

The codebase follows the bundled Next.js 16 rules (AGENTS.md): Turbopack is the default (no custom webpack config), all request-time APIs are async (await on cookies(), headers(), params, searchParams), DB/session routes are runtime = "nodejs" + dynamic = "force-dynamic" (Prisma, the Anthropic SDK and pdfkit need the Node runtime, never Edge), long work uses after() to schedule the next pipeline stage after the 202 response, and auth middleware uses the proxy.ts convention.

12.3 Deployment & ops

Local: npm install, set ANTHROPIC_API_KEY, npx prisma migrate dev, npm run db:seed, npm run dev. Production (Vercel + Turso + Blob): set TURSO_DATABASE_URL, TURSO_AUTH_TOKEN, BLOB_READ_WRITE_TOKEN, SESSION_SECRET, ADMIN_TOKEN, CRON_SECRET and SEED_ANCHOR, apply the schema to Turso, deploy, and provision data via the admin endpoint. Two Vercel crons run the B2 monitoring sweep and the stalled-pipeline resume sweeper; both are also triggerable in-app.
